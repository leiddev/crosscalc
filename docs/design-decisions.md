# 设计决策记录

本文记录 crosscalc 里那些「本来可以那样做，但最后选成这样」的决定，以及背后的理由。
每一条都写明了**为什么不选另一种做法**。后面维护时如果想把某个决定改回去，
先看看这里记的坑。

---

## 1. 计算全部交给 tinyexpr-plusplus，不自己写计算函数

需求里明确要求「尽量使用该库的计算功能，不要自己编写计算函数」。这条边界是这样切的：

| 层次 | 归谁 |
|---|---|
| 表达式解析、优先级、括号、函数调用 | tinyexpr-plusplus |
| 全部数学运算、三角函数、位运算函数 | tinyexpr-plusplus |
| 模式的输入校验（位数、进制、字长是否合法） | 本项目 |
| 错误信息的中文化与定位 | 本项目 |
| 结果的**显示格式**（进制、分组、符号） | 本项目（显示层，不做数学） |

`src/core/number_format.cpp` 里的 `format_programmer()` 会把两补码位型取出来显示成
`FF` / `377` / `11111111`，这看起来像「自己做运算」，但实际只有 `static_cast`、
按位掩码和移位，**没有任何算术**。真正的进制转换（`hex2dec` 之类的反向转换库不提供，
见第 5 条）是字符串层面的重排，不是计算。

**不选的做法**：用 C++ 的 `%` / `>>` 自己拼一个进制转换器，或自己写一个
「表达式解析器」。前者会绕过库已有的精度与溢出语义，后者直接违反需求。

## 2. `^` 保持乘方语义，位运算走 `BITAND()` / `BITOR()` / `BITXOR()` 函数

tinyexpr++ 有一个编译期开关 `TE_BITWISE_OPERATORS`，打开后 `^` 会变回按位异或
（C 语言传统语义）、`&` 与 `|` 的优先级也会跟着调整。

**本项目不定义这个宏**，因此：

- `^` 是乘方（`2^10 == 1024`），`**` 是它的同义写法；
- 按位与/或/异或分别写成库提供的 `BITAND(x, y)` / `BITOR(x, y)` / `BITXOR(x, y)`；
- `&` 和 `|` **永远是逻辑运算符**（`&&` / `||` 的简写），**不受这个宏影响**——
  这一点很容易误解，即使打开 `TE_BITWISE_OPERATORS`，`&` 仍然不是按位与。

**为什么**：科学模式里 `2^10` 必须是 1024，这是用户的直觉预期；程序员模式里
位运算又有专门的函数按钮可用。如果打开宏，科学模式的乘方就得改写成 `pow(2,10)`，
键盘和教学场景都会变难用。把 `&` 的「永远是逻辑运算符」写进测试用例，
免得以后有人以为打开宏就能救回 C 语言语义。

→ 回归用例：`tests/test_calc.cpp` 的 `programmer: && 与 || 的简写是逻辑运算`。

## 3. 8/16/32 位字长在所有平台精确，64 位只在支持时提供

tinyexpr++ 的位运算用 `te_type` 做中间类型，能不能装下 64 位整数取决于它的精度。
`te_parser::supports_64bit()` 的实现就是 `numeric_limits<te_type>::digits >= 64`，
而 `te_type` 默认是 `double`，只有定义了 `TE_LONG_DOUBLE` 才变成 `long double`：

| 平台 | `long double` | `TE_LONG_DOUBLE` | 能精确表示的最大整数 |
|---|---|---|---|
| Linux / macOS (x86-64, GCC/Clang) | 80 位扩展精度 | 定义 | 2^64 − 1 |
| Windows / MSVC | 与 `double` 相同 | 不定义（定义了也没用） | 2^53 − 1 |
| Apple Silicon | 与 `double` 相同 | 不定义 | 2^53 − 1 |

所以：

- **8 / 16 / 32 位字长在两个平台上都是精确的**，随便用；
- **QWORD(64) 只在 `supports_64bit()` 为真时开放**。Windows 上点了 64 位会得到一条明确的说明
  （而不是静默给出被截断的结果）；
- 库自身的位运算参数上限是 `te_parser::MAX_BITOPS_VAL` = 2^48 − 1，超出会抛异常；
  注意它是**含** 2^48 − 1 的，写边界用例时别把 `0xFFFFFFFFFFFF` 当成越界。

前端不做平台判断，`/api/platform` 返回 `supports_64bit`，界面据此把 QWORD 按钮置灰。

**为什么不「统一按 32 位算」以回避差异**：程序员模式不做 64 位就少了一大块，
而 Linux 上完全能做对。让能力随平台可见地变化，比悄悄降级更好。

### 3.1 判断条件必须用「试编译」，不能看平台名或 `sizeof`

CMake 里用 `check_cxx_source_compiles` 试编译一句
`static_assert(numeric_limits<long double>::digits >= 64)`，
通过才给 tinyexpr++ 加 `TE_LONG_DOUBLE`。**不能**写成 `if(MSVC)`、
也不能用 `CMAKE_CXX_SIZEOF_LONG_DOUBLE`：后者在部分 CMake 版本/平台上根本不存在，
实测在 Ubuntu 22.04 + CMake 3.22.1 上取到空值，条件静默为假 ——
**QWORD 就此退化成 53 位，不报错、不警告**，只有把向量跑起来才会发现。
用和库完全相同的判据试编译，就不存在这种口径不一致。

### 3.2 `TE_LONG_DOUBLE` 必须是 PUBLIC 编译定义

`te_type` 出现在 `te_parser` 的**公开接口**上（`evaluate()` 的返回值等）。
如果只有 `tinyexpr.cpp` 带着这个宏、而 `calc_engine.cpp` 不带，
两边对同一个函数的返回值类型理解不一致（`long double` vs `double`），
就是 ODR 违反 + 调用约定错乱，运行时结果不可预测。
所以它在 `crosscalc_tinyexpr` 上是 `PUBLIC`，并且 `crosscalc_core` 用
`PUBLIC` 链接它，一路传到所有消费者。

### 3.3 全链路不许窄化，否则 64 位精度会静默丢失

这是本项目最隐蔽的一个 bug：`calc_engine.cpp` 里曾经有一行

```cpp
const double value = static_cast<double>(raw);   // ← 错的
```

于是 `0xFFFFFFFFFFFFFFFF`（2^64−1）在**进入显示层之前**就被舍入成 2^64，
程序员模式显示 `18446744073709551616` 而不是 `FFFFFFFFFFFFFFFF`。
现在全程用 `num_t`（`long double`，见 `src/core/calc_types.h`），
并且有 `static_assert(sizeof(num_t) >= sizeof(te_type))` 挡住把它改窄的改动。

**只有在「显示」这一步**才按 double 精度收敛，理由见第 12 条。

→ 回归用例：`tests/test_calc.cpp` 的「引擎能力」一组；`tests/vectors/programmer.json`
里 5 条 QWORD 用例带 `requires_64bit`，在不支持的平台上自动跳过。另有 1 条 `arith: "extended"`
与 2 条 `arith: "double"` 用例，见第 12 条。

## 4. 三类失败必须归一化成同一种「友好错误」

tinyexpr++ 有**三种互不相同的失败方式**，如果只写一个 `if` 判断，会漏掉两种：

| # | 表现 | 例子 |
|---|---|---|
| 1 | 抛 `std::runtime_error` | `1/0`、`sqrt(-1)`、位运算参数越界 |
| 2 | `success() == false`，且 **`get_last_error_message()` 是空字符串** | 语法错误、未知符号——**只给位置，不给说明** |
| 3 | **静默返回 NaN 但 `success() == true`** | `HEX2DEC("ZZ")` |

第 2 类是最难处理的：位置是**0-based**，而 `te_parser::npos == -1` 表示「没有位置」。
本项目在 `error_text.cpp` 里根据位置 + 上下文重建说明：括号不匹配、表达式被截断、
未知符号/函数（把 `'名字'` 引出来）、以及运算符后缺操作数。

**如果不处理第 3 类**，界面会显示一个 `NaN` 而没有任何提示，用户完全不知道
`ZZ` 不是合法的十六进制。

`Engine::evaluate()` 承诺**永不抛异常**，调用方不必写 try/catch。

→ 回归用例：`tests/vectors/errors.json`（58 条专门跑错误路径）。

## 5. 进制输出放在显示层，因为库只提供单向转换

库只提供 `HEX2DEC` / `BIN2DEC` / `OCT2DEC`（字符串 → 数值），**没有反向转换**。
所以把结果同时显示成 hex/dec/oct/bin（程序员模式右侧那一列）必须在显示层做。

为了避免前端重复实现位运算，**四种进制的值全部由后端算好**放在 `all_bases` 字段里，
前端只负责贴字符串。这样「掩码 → 符号扩展 → 进制」只有一份实现（`number_format.cpp`），
不会出现前后端算法漂移。

→ 回归用例：`tests/e2e_api.py` 里对 `all_bases` 的断言。

---

## 6. 不用 `std::format`，用 `snprintf`

CI 的 Linux 目标是 ubuntu-22.04（GCC 11），而 libstdc++ 在 GCC 13 才有 `<format>`。
用 `std::format` 会让 Linux 构建直接失败，而 GCC 11 又没有好用的替代，
所以统一用 `snprintf` 拼字符串。

**同理刻意保留的写法**：不依赖 C++23 的 `std::print`，不用 `std::to_chars` 的浮点重载
（GCC 11 的实现不完整）。

## 7. MSVC 必须加 `/Zc:__cplusplus`

MSVC 默认把 `__cplusplus` 报成 `199711L`。tinyexpr++ 里有 8 个旋转函数
（`BITLROTATE8/16/32/64`、`BITRROTATE8/16/32/64`）用
`#if __cplusplus >= 202002L` 保护——不加这个开关，它们会被**静默编译掉**：
不报错，只是在按到那个按钮时提示「未知函数」。

`CMakeLists.txt` 里 MSVC 的 `add_compile_options` 必须保留 `/Zc:__cplusplus`。
同一个选项也会传给 `crosscalc_tinyexpr`（它是独立的静态库 target，不会继承
外层目录的 `add_compile_options` 之外的东西）。

→ 回归用例：`tests/vectors/programmer.json` 里的 `bitlrotate8/bitrrotate8` 用例。
**这条最值得警惕**：它是「编译得过、测试才发现」的静默失败。

---

## 8. 第三方源码的警告全部关掉，但测试必须开 `/W3`

`crosscalc_tinyexpr` 用 `/w`（MSVC）/ `-w`（GCC）编译上游 `.cpp`。
上游代码本来就不是按本项目的警告等级写的，我们没有修改它的权利，
而一堆第三方警告会把**本项目的**警告淹掉。

本项目的代码（`crosscalc_core`、`crosscalc`、`crosscalc_tests`）保持
MSVC `/W3`、GCC `-Wall -Wextra` 全开。

## 9. 测试分四层（Linux 还有第五层），CI 必须全部跑绿

| 层 | 命令 | 覆盖什么 | 需要什么 |
|---|---|---|---|
| ① 单元 + 黄金向量 | `ctest --preset <平台>-release` | 计算逻辑、错误信息、边界 | 什么都不要 |
| ② HTTP 端到端 | `python tests/e2e_api.py` | 真实进程 + 内嵌资源 + API 契约 | 能起进程 |
| ③ 前端一致性 | `python tests/check_frontend.py` | 键盘 ↔ 引擎函数表、DOM id、模式集合 | 测试二进制 + node |
| ④ app.js 纯函数 | `node tests/js_frontend_test.js` | 二进制/八进制 → `0x` 的重排 | node |
| ⑤ GUI 冒烟（仅 Linux） | `bash tests/smoke_gui.sh` | GTK + WebKitGTK 渲染链路 | Xvfb |

第①层的两个测试都要求打印 `ALL TESTS PASSED`（`PASS_REGULAR_EXPRESSION`），
否则 ctest 仍会判失败——**防止测试程序崩在中途却因为退出码是 0 而算过**。

**为什么值得加第③层**：最容易出的 bug 是「前端加了按钮，键名和引擎的函数名不一致」，
这类问题只有真的按下去才会暴露。静态比对一遍引擎的函数表，几毫秒就能挡掉。

**为什么值得加第④层**：二进制/八进制数字键要把数字重排成 `0x` 字面量（见第 11 条），
算错了**界面完全不会报错**，只是静静地显示成另一个数。所以拿 BigInt
（V8 自己的进制转换）当独立的第二实现，随机取 300 组对照。
这一层当场抓出了一个真实错误：八进制位数上限原本写成 `ceil(bits/3)`，
QWORD 下 22 位就是 66 bit，会溢出字长，正确答案是 `floor(bits/3)` = 21 位。

**为什么第②层用 `--headless`**：Windows 的 CI 没有交互式桌面会话，
webview 创建窗口可能失败，而失败时会弹**模态提示框**把任务挂到超时。
`--headless` 只起 HTTP 服务，不碰 GUI，稳定且快。

**第②层的一个坑**：子进程的输出**不能接到 `subprocess.PIPE`**。程序每处理一个请求
都写日志，管道 64KB 缓冲写满后子进程会阻塞在写日志上，整个测试死锁（实测挂满 300 秒）。
现在输出重定向到临时文件，需要时再读。

**第⑤层能验证什么**：无头环境里唯一能拿到的"渲染链路真的通了"的证据，
是程序日志里出现**窗口自己发起的** `GET /app.js` —— 说明 GTK/WebKitGTK 真的把页面加载起来了。

## 10. 已知限制（都是有意为之，不是没做完）

| 限制 | 说明 |
|---|---|
| `log2` / `sec` / `csc` / `asinh` / `gcd` 等不支持 | 库不提供，按约定「暂不支持此类运算」 |
| `%` 是取模，不是 C 的按位取余 | 库定义如此，程序员模式用 `BITAND` 等函数做位运算 |
| 角度制（DEG / GRAD）不支持 | 只支持弧度，界面上有说明 |
| 不支持 `0b1010` / `0o17` 字面量 | 库不识别；二进制/八进制数字键会无损换算成 `0x`（见第 11 条） |
| `&` / `|` 是逻辑运算 | 见第 2 条 |
| Windows 上不做 64 位字长 | 见第 3 条 |
| 浮点显示最多 17 位有效数字 | 见第 12 条 |
| `HEX2DEC` 等最多 10 位数字且有符号语义 | 见第 11 条 |

这些限制在 `tests/test_calc.cpp` 的「已知限制」一组里**被写成了测试**——
如果哪天上游补齐了这些能力，测试会失败，提醒我们回来更新文档。

## 11. `HEX2DEC` / `BIN2DEC` / `OCT2DEC` 不是通用的进制转换函数

读源码（`tinyexpr.cpp` 里这三个函数的实现）才看清楚，它们的真实行为很反直觉：

| 函数 | 参数长度上限 | 凑满上限时的符号语义 |
|---|---|---|
| `bin2dec` | 10 | 10 位二进制，首位为 1 则减 2^10 → **有符号 10 位** |
| `oct2dec` | 10 | 30 位八进制，≥ 2^29 则减 2^30 → **有符号 30 位** |
| `hex2dec` | 10 | 40 位十六进制，≥ 2^39 则减 2^40 → **有符号 40 位** |

两个后果：

1. **超长直接得到 NaN**（不是抛异常），属于第 4 条里的第 ③ 类失败。
   界面上必须翻译成人话，否则用户只会看到"没有结果"。
   `friendly_invalid_result()` 因此会把参数里的字符串抠出来数位数，
   超过 10 位时直接说明上限，并提示改用 `0x` 字面量。
2. **`BIN2DEC("1111111111")` 是 −1，不是 1023。** 这绝不能拿来做输入通道。

所以程序员模式的输入设计成：

- 十进制 → 原样写（引擎原生支持）；
- 十六进制 → `0x` 字面量（引擎自己的字面量解析是精确的，能到 64 位，没有 10 位限制）；
- 二进制 / 八进制 → **按 4 位一组重排成 `0x` 字面量**：
  1 位二进制 = 1 bit、1 位八进制 = 3 bit，左侧补 0 到 4 的倍数后逐组查表。
  全程只有查表与字符串拼接，**没有任何算术**，也没有精度损失 ——
  和"显示层负责进制换算"是同一个性质。
  位数上限取 `floor(字长/3)`（八进制）而不是向上取整，否则 QWORD 下会超出字长。

进制换算的**权威实现仍然在后端**（`/api/eval` 的 `all_bases` 字段，前端不做任何位运算）；
前端这一步只是把用户敲的按键组成一个合法的输入字面量。

→ 回归用例：`tests/vectors/programmer.json` 里那几条带 `note` 的转换用例；
`tests/test_calc.cpp` 的「已知限制」；JS 侧是第 9 条的第④层。

## 12. 显示精度统一收敛到 double（17 位有效数字）

`format_general()` 用 `(double)v` 做"最短且能唯一还原"的格式化，
**不**按 `num_t` 的 80 位扩展精度如实展开。理由：

- 80 位如实展开会得到 `0.1+0.2 = 0.300000000000000000011` 这种噪声，
  有效信息没增加多少，可读性却没了；
- 同一个表达式在两个平台上必须显示成同一个字符串，否则黄金向量没法共用，
  用户也会觉得"换个系统答案就变了"。

代价是**少数用例在两个平台上的正确答案本来就不同**，这不是 bug：

| 表达式 | double 平台 | 扩展精度平台 |
|---|---|---|
| `0.1+0.2` | `0.30000000000000004` | `0.3`（加数误差在更高精度里抵消） |
| `cot(pi/4)` | `1.0000000000000002` | `1` |
| `sin(pi/6)` | `0.49999999999999994` | `0.5` |
| `1e999` | 溢出报错 | 正常求值（没超出 long double 上限） |

处理办法是向量里加一个 **`arith` 字段**（`"double"` / `"extended"`），
标明这条用例只在哪种运算精度下成立，另一个平台上自动**跳过**；
`1e9999` 两者都溢出，就不需要标注。

`tests/test_calc.cpp` 里遇到同类断言时，**两个分支都写出来**：

```cpp
if (crosscalc::Engine::supports_64bit()) CHECK_EQ(display, "0.3");
else                                     CHECK_EQ(display, "0.30000000000000004");
```

——每条分支在自己的平台上都真的被断言过，而不是放宽成 `CHECK_NEAR` 一了百了。

**别忘了两边都得改**：`arith` 门控在 `vector_runner.cpp` 和 `e2e_api.py` 里各有一份，
逻辑必须一致，否则会出现"一边跳过、一边判失败"。

## 13. 自测脚本必须能识别"我到底在跟谁说话"

`smoke_gui.sh` 不写死端口，并且做了三件事：
启动前确认端口是空的；启动后从 `/api/info` 读回 PID，确认应答的就是刚启动的那个进程；
清理时用这个 PID 而不是 `$!`（`xvfb-run` 是个脚本，`$!` 拿到的是它自己，
kill 它不一定能带走真正的 `crosscalc`）。

**为什么值得这么较真**：实测被坑过一次——上一轮残留的实例占着写死的端口，
curl 打到的其实是**上一个进程**，返回 404，而错误信息看起来像是新进程的问题，
排查方向完全被带偏。

## 14. 「还没输完」和「敲错了」必须分开

输入框每变一次就求值一次（90 ms 防抖），这意味着用户每敲一个字母都会触发一次求值。
如果失败一律弹红框，那么敲 `2+`、`sin(`、手打 `sqrt` 的整个过程里红框会一直闪，
用户看到的全是"错误"，而其实什么都没做错。

所以 `EvalResult` 上多了一个 **`incomplete` 标记**（JSON 里同名），
`diagnose_syntax_error()` 在给出中文提示的同时，也判定这条失败属于哪一类：

| 情形 | 例子 | `incomplete` |
|------|------|--------------|
| 少右括号 | `sin(`、`((1+2)`、`3*(4+` | `true` |
| 表达式被截断 / 末尾缺操作数 | `2+`、`2+3*`、`1/`、`2**` | `true` |
| 只有孤零零一个运算符 | `+` | `true` |
| 名字顶在末尾（正在一个字母一个字母敲函数名） | `s`、`sqr`、`1+bar` | `true` |
| 空输入 | `""`、`"   "` | `true` |
| 多右括号 / 以运算符开头 / 两个运算符挨着 | `1+2)`、`*3`、`2+*3` | `false` |
| 未知函数、数字写错 | `nosuchfn(1)`、`1.2.3`、`0b1010` | `false` |
| 计算期错误（除零、NaN、溢出） | `1/0`、`sqrt(-1)` | `false` |

前端 `errorIsPending()` 只做一件事：**实时预览**（没有 `commit`）时，把带标记的错误压住——
结果区显示灰色的 `—` 和一句"表达式还没输完，继续输入…"，不弹红框、不写历史；
用户按下等号/回车（`commit: true`）时才把错误摆出来。
真正的错误（除零、`2+*3`）没有标记，照旧**立刻**报，用户不用等到按等号才知道写错了。

几个刻意的取舍：

- **判定放在后端**，前端不做任何词法/语法判断（沿用「前端只管输入法和渲染」的分工）。
  因此 `friendly_syntax_error()` 改成了返回 `SyntaxDiagnosis{text, incomplete}` 的
  `diagnose_syntax_error()`——**提示文本一个字没改**，向量里原有的 `error_contains` 断言全部照旧。
- **数字开头的 token 不享受"还在打字"待遇**（`1.2.3`、`0b1010`、`1 2` 都是 `false`）。
  只有以字母/下划线开头、且一直顶到表达式末尾的名字才算——那才可能是"`sqrt` 才打到 `sq`"。
- **`2**` 是"没输完"，`2**3` 是合法表达式**（`**` 是幂运算，见 `standard.json`），
  别把它当成"两个运算符挨着"写进向量里。
- 向量和 e2e 都加了 `expect_incomplete` 字段（`vector_runner.cpp` 与 `e2e_api.py` 各断言一次），
  并且**成功时 `incomplete` 必须为 `false`**，否则前端会把好结果当成"没输完"压住不显示。
  这条约束同样写在 `tests/check_frontend.py` 的字段契约检查里（少读这个字段就报错）。

## 15. 键盘必须钉在原地：错误区高度写死，键盘不许被压缩

上一节解决了"错误什么时候该弹"，这一节解决"弹出来的时候别乱动"。

### 错误提示区占固定高度

错误框**不是** `hidden` 显示/隐藏，而是永远占着 `--error-slot`（80px）那么高，
没出错时只把内容用 `.error-box.is-empty { visibility: hidden }` 藏起来：

```css
.error-box          { height: var(--error-slot); overflow: auto; }
.error-box.is-empty { visibility: hidden; }
```

如果换成 `hidden` 属性或 `display: none`，元素高度会塌成 0，错误一来一去整块键盘
就跟着上下跳 40px——而这恰恰是打字最频繁的时刻。`visibility: hidden` 保留占位，
所以下面的键盘**一像素都不动**（用 headless 浏览器量过：位移 0px）。

两个连带的约束：

- **80px 是量出来的，不是拍的。** 内容是"两行提示（13px×1.35）+ 两行定位
  （12px×1.2，一行表达式一行 `^`）"，实测 76px。调小就会把 `^` 挤到可视区外，
  调大就是白占键盘的地盘。更长的提示在框内自己滚，绝不往外顶。
- **`^` 箭头必须落在预算内。** 表达式长度没有上限，整条铺出来会撑出横向滚动条，
  滚动条又要吃掉一行高度，等于把箭头弄丢。所以 `app.js` 的 `caretWindow()`
  以出错处为中心截一段（默认 72 字符，两头用 `…` 收尾）。
  它守住两条不变量，`tests/js_frontend_test.js` 逐条断言：
  `badWidth >= 1`（光标停在末尾时也得有个 `^` 指着）、
  `head.length + badWidth <= budget` 且整行也不超预算。

### 键盘宁可撑出滚动条，也不能被压扁

`.calc` 是 flex 列，里面只有键盘是可压缩的。窗口一矮，flex 会一路把键盘压到
**0 高**——按键全部消失（程序员模式 6 行最先撞上）。所以：

```css
.calc     { overflow-y: auto; }  /* 装不下就让整列滚，别动孩子 */
.keypads  { flex: 1 0 auto; }    /* flex-shrink 必须是 0 */
.kp-row   { min-height: 40px; }  /* 再挤也要保住一行的高度 */
```

### 高度是挤出来的：40px 的行高、四行的进制面板

`.kp-row` 的 `min-height` 同时是程序员模式可读性的下限——按键上的 `2nd`、`HEX`、
`÷` 要看得清，靠的是**字号**（功能键 15px、数字 17px、运算符 20px、等号 21px）
和**行高**一起。之前的拥挤主要来自字号偏小（功能键 13px）和禁用态对比度太低
（opacity .3），这两条已经改掉（现在 opacity .45）。

那为什么是 40px 而不是 44px？因为"程序员模式 6 行键盘 + 四行进制面板 + 默认窗口
1180×820"三者是互相抢高度的：

| 块 | 高度 |
| --- | --- |
| 显示区（表达式 21px + 结果 32px） | 93 |
| 错误提示区（固定占位） | 80 |
| 进制面板（四行读数 + 字长按钮 + 提示行） | 172 |
| 键盘（6 行 × 40 + 5 × 6 行距） | 270 起 |
| 三个 6px 间隔 | 18 |
| **合计下限** | **633**（可用 640） |

当初把进制面板压成两行（hex/dec/oct 并排、bin 独占一行）就是为了这 50px，
但那让四种读数互相抢宽度。**四行读数比 4px 行高重要**——所以面板还原成
"一种进制一行"，高度让键盘的 `min-height` 从 44 收到 40，另外把 `.calc`/`.keypads`
的间距 8→6、`.display` 内边距 9→8、`.base-row` 内边距 4→2 各让一点。
字号一个没动：**挤的是空白，不是字。**

顺带删掉了提示区常驻的"本平台不支持 QWORD"警告。那是引擎的先天限制、用户改不了，
天天挂一行在最显眼的位置喊"你少个功能"，只会让人以为哪里坏了。QWORD 按钮该灰还是灰，
原因挂在按钮的 `title` 上（`tests/check_frontend.py` 会盯着"置灰 + title"还在）。

### 这类约定用静态检查钉住

"错误区高度写死"和"键盘不许收缩"是纯 CSS 行为：C++ 单测、JS 纯函数测试都碰不到，
而回归起来极其显眼、又极其容易被好心改坏（"用 `hidden` 更语义化"、"窗口小的时候
键盘紧凑点更好看"）。所以 `tests/check_frontend.py` 里加了 `check_layout_anchors()`：
直接检查 `:root` 有没有 `--error-slot`、`.error-box` 高度是不是 `var(--error-slot)`、
`.is-empty` 用的是不是 `visibility`、`html` 里有没有偷偷用回 `hidden` 属性、
`.calc` 滚不滚、`.keypads` 是不是 `flex: 1 0 auto`、`.kp-row` 有没有 `min-height`、
进制读数是不是一种一行（四行面板是明确要求的，压成两行读数就会互相抢宽度）。
这几个断言都验证过"改坏就报错"。
