## v0.1.1 — 第一版里那几处一眼能看出的毛病

`v0.1.0` 发出去之后，对着界面一块一块看下来发现的问题，这一版全部收掉：
输入过程中一直在报错、错误提示推着键盘跳、科学模式按键压成一条、
清零键几乎永远点不动、窗口一上来占满屏、还有「关于」里永远写着「运行时长 0 秒」。

**没有新增功能，也没有动求值行为**：表达式解析、优先级、错误文案、进制换算
全部照旧，改的是前端布局、按键可用性判断、窗口尺寸和一个取数时机。
所以按 SemVer 走补丁号 `0.1.1`。

### 修好的问题

- **打字全程都在报错**：每按一个键都会求值一次（90ms 防抖），而 `2+`、`sin(`、
  手打 `sqrt` 的每一拍都是失败，之前一律弹红框。现在后端在 `EvalResult` 里给出
  `incomplete` 标记（少右括号 / 被截断 / 末尾缺操作数 / 名字还顶在末尾 / 空输入），
  判定这段是「还没输完」时前端压住错误，结果区显示灰色的 `—` 和一句
  「表达式还没输完，继续输入…」，不弹红框也不写历史；按等号 / 回车时照旧报错。
  提示文本一个字没改，原有向量的 `error_contains` 断言全部照旧。
- **一出错整块键盘往下跳**：错误框的内容用 `hidden` 藏起来时高度会塌成 0，
  错误一来一去键盘就跳 40px。改成把高度写死成 `--error-slot`（80px，
  两行提示 + 两行定位量出来的），平时只藏内容不藏盒子。
  实测键盘顶部 401px → 401px，位移 0。
- **科学模式按键糊成一团**：`SPLIT` 切出来的「函数块 | 数字块」内部是
  `flex-direction: column`，6 行等于要 24 个键的高度，结果每个键被压成 14px、
  行与行互相盖住（`asin` 压着 `pi`）。改成块内 `flex-direction: row`
  （一行就是一格键的高度），两块的缝加宽到 14px。这个坑从 `v0.1.0` 就在。
- **清零键几乎永远点不动**：按键「在这个进制下能不能敲」的判断是按 **label**
  查 `0-9/A-F` 表的，而清零键的标签正好是 `C` = 十六进制 12，于是它在
  DEC / OCT / BIN 下一律被灰掉——连标准、科学模式也遭殃（那两种模式的进制固定是 dec）。
  按建议把标签改成 **`AC`**（两个字符，天然不参与这个判断），
  顺带也解决了程序员模式里「十六进制数字 C」和「清零 C」同名的问题。
  `C` 这个名字不许改回去，`tests/check_frontend.py` 里有一条静态检查守着。
- **进制面板回到「一种进制一行」**：上一版为了省 50px 把 hex/dec/oct 压成并排、
  `bin` 独占一行，代价是四种读数互相抢宽度、位数长的得左右滚。现在恢复四行、
  字号回到 16px，高度从空白里挤（间距、内边距、键盘行高 44→40），不挤字。
  同时删掉了提示区那条常驻的「本平台不支持 QWORD…」——引擎的先天限制天天挂在
  最显眼的位置只会让人以为哪里坏了，QWORD 按钮该灰还是灰，原因仍在它的 `title` 里。
- **初始窗口太大**：`1180×820` → **`1024×720`**，最小尺寸仍是 `760×560`。
  这个尺寸是量出来的下限附近：窗口高低于约 714 时程序员模式开始在结果区里滚动，
  宽低于约 901 会切成「记录区放到下面」的单列布局。
- **「关于」里的运行时长永远 0 秒**：后端没错（`uptime_ms` 是活的），
  错在前端只问了一次——启动时取一次 `/api/info` 就把「运行时长 N 秒」烤进了 HTML，
  而那时进程刚起来几百毫秒，`Math.round(0.3) = 0`，之后再也不会变。
  现在每次打开对话框都重取一次（取数 + 渲染抽成 `refreshAbout()`），
  后端所有 API 回复统一带上 `Cache-Control: no-store`（都是「此刻的事实」）。

### 这次踩到的两个量测陷阱

两条都写进了 [docs/design-decisions.md](https://github.com/leiddev/crosscalc/blob/main/docs/design-decisions.md)，
因为它们都属于「自测全绿、结论却是反的」那类错误：

- **改了 `www/` 就必须重新编译**：前端是在构建期被 `cpp-embedlib` 嵌进可执行文件的
  （`_data_*.cpp`），运行时读内存、不读磁盘。有一次改完 `app.js` 只跑了
  `ctest` / `e2e_api.py`（这两层都不碰前端）就以为好了，其实 exe 里还是旧界面。
  现在的验收方式是：重新构建后，用 `--headless` 起真进程去取 `/app.js`，
  跟磁盘上的文件逐字节比对，一致才算数。
- **`set_size` 给的是视口，不是窗口**：`set_size(1024, 720)` 出来的是
  `1038×757` 的窗口（边框 14×37），页面里 `innerHeight` 是 721。
  用 headless Edge 量这个 app 时 `--window-size` 要传「视口 + 32/96」，
  否则凭空的 96px 会让结论反过来：按 `1024×720` 量出 `.calc` 只有 540px、
  断言「程序员模式肯定要滚动」，按真实视口量是 638px、三种模式全装得下。
  另外这台机器 `devicePixelRatio` 是 1.75（175% 缩放），量测得跟着设。

### 自测

两个平台各自跑完全部自测，CI 才绿：

| 层 | Windows | Linux |
|---|---|---|
| ① 单元测试 | 44 用例 / 265 断言 | 44 用例 / 266 断言 |
| ① 黄金向量（共 334 条） | 执行 328 条（跳过 6 条）/ 686 断言 | 执行 332 条（跳过 2 条）/ 694 断言 |
| ② HTTP 端到端（同一批向量经真实进程回放） | 1381 断言 | 1398 断言 |
| ③ 前端一致性 | 74 条通过（含 Node 实跑） | 同 |
| ④ app.js 纯函数 | 368 断言（300 条与 BigInt 对照） | 同 |
| ⑤ GUI 冒烟（Xvfb） | —（无桌面会话） | 通过，日志里可见窗口自己拉的 `/app.js` |

跳过的条数两边仍然不同，而且仍然是设计目标：334 条里 5 条打 `requires_64bit`、
1 条打 `arith: "extended"`、2 条打 `arith: "double"`，Windows 只跳前 6 条、
Linux 只跳后 2 条。

上表数字这一版开始都能在 CI 日志里复核：以前 CTest 只在失败时吐输出，
这些「多少用例 / 多少断言」只有本机跑过的人知道，所以两个平台的构建步骤里
各加了一行，把测试程序的汇总行直接打进日志（不额外构建、不做新检查）。

这一版新增的检查（都验证过「改坏就报错」）：实时预览压错误的字段契约、
错误框高度不许塌、科学模式两块必须并排、按键标签不许撞数字表、
「关于」的打开必须重新取数、以及端到端侧的 `uptime_ms` 必须真的在涨。

### 已知限制

与 `v0.1.0` 相同，这一版没有动这些：

- **macOS 未验证**：代码里留了 WKWebView 的分支，但构建脚本和 CI 都没覆盖。
- **Windows 上不做 64 位字长**（MSVC 的 `long double` 与 `double` 同宽），QWORD 按钮置灰。
- **只支持弧度**，没有 DEG / GRAD。
- **`log2` / `sec` / `csc` / `asinh` / `gcd` 等不支持**：库不提供。
- **按位运算参数上限 2^48−1**：库自身的限制，超出会给出明确提示。
- **浮点结果显示最多 17 位有效数字**：两个平台保持一致。
- **没有安装包**：产物就是单个可执行文件，Windows 侧依赖系统的 WebView2，
  Linux 侧依赖系统的 WebKitGTK。
